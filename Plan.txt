A.E.G.I.S. — Технический план реализации Phase 1

Целевая платформа: Ryzen 5 / 16 GB RAM / Ollama
Модели: qwen2.5:7b (~6 GB VRAM, 35–55 tok/s) для рутинных задач, qwen3.6:27b Q4_K_M (~20 GB VRAM с 16K ctx, 25–35 tok/s) для сложного кодинга и рефлексии; на 16 GB RAM одновременно держать обе модели нецелесообразно — роутер должен выгружать неактивную модель через keep_alive: 0 или переключать OLLAMA_MAX_LOADED_MODELS=1.
Философия: «Контракт вместо кода». Любая замена реализации (SQLite → PostgreSQL, ChromaDB → Qdrant, python-docx → кастомный OOXML-рендерер) не трогает вызывающий код.

EP1.ST3 — Capability Registry с разрешением зависимостей

Суть: Реализовать реестр, в котором адаптеры регистрируются по строковому ключу и разрешаются по Protocol-типу через isinstance(impl, runtime_checkable_protocol) или явный provides-список. Никаких прямых импортов адаптеров в бизнес-логике.
Файлы:

· src/aegis/core/registry.py — класс CapabilityRegistry:

  · resolve(contract: type[T]) -> T — если зарегистрировано несколько кандидатов, бросает AmbiguousCapabilityError с перечнем; если ноль — MissingCapabilityError.
  · list_capabilities() -> dict[str, list[str]].
· tests/test_registry.py — тест: два фейковых LLM-адаптера, resolve(AbstractLLM) возвращает зарегистрированный по умолчанию.

EP1.ST4 — Локальная асинхронная Event Bus

Суть: In-process pub/sub на asyncio.Queue. Никакого Redis/NATS в Phase 1. Гарантия: событие доставляется всем подписчикам, подписавшимся до публикации; подписчики, подписавшиеся после, не получают ретроспективу.

· tests/test_event_bus.py — тест: подписчик получает событие, опубликованное после подписки; не получает — до.

DoD: pytest tests/test_event_bus.py зелёный; таймаут подписки 30 с (тест не виснет вечно).
Extension Point: Замена на Redis Streams или NATS — новый класс, реализующий AbstractEventBus, регистрируется в CapabilityRegistry; бизнес-код не меняется.

ЭПИК 2: Единое Промежуточное Представление (IR) и Двусторонняя Память

Суть: Спроектировать таблицы L1: сессии, версии IR-дерева, learned_patterns, modification_log. Версионирование IR — через parent_version (DAG, не линейная история), чтобы поддерживать ветвление при ручных правках.

  · learned_patterns(id TEXT PRIMARY KEY, task_signature TEXT NOT NULL, pattern_json TEXT NOT NULL, success_count INTEGER DEFAULT 1, last_used_at TEXT)
  · modification_log(id INTEGER PRIMARY KEY AUTOINCREMENT, doc_id TEXT, from_version TEXT, to_version TEXT, diff_json TEXT NOT NULL, source TEXT CHECK(source IN ('agent','human')), created_at TEXT).
  · Индексы: idx_versions_doc ON document_versions(doc_id, created_at DESC), idx_patterns_sig ON learned_patterns(task_signature).

EP2.ST3 — Схема IR (JSON Schema) как единый контракт документа

Суть: Определить document_ir.schema.json (draft 2020-12), от которого зависят все компиляторы и валидаторы. IR — это типизированное намерение, а не байты OOXML: модель не пишет XML, она заполняет IR.

  · Block — oneOf: {type:"heading", level:1-6, text}, {type:"paragraph", runs:[{text, bold?, italic?}], style?}, {type:"table", columns:[...], rows:[[...]], header_row:bool}, {type:"image", ref, width_cm?, height_cm?}, {type:"list", ordered:bool, items:[...]}.

EP2.ST4 — Двусторонняя синхронизация IR ↔ modification_log

Суть: Любая ручная правка в WYSIWYG (пока — программная, через API) порождает diff между from_version и to_version в формате RFC 6902 (JSON Patch) и пишется в modification_log. Агентские правки пишутся туда же с source:"agent".

DoD: pytest tests/test_ir_diff.py: patch round-trip (apply_patch(old, diff_ir(old, new)) == new).
Extension Point: При переходе на OT/CRDT (для real-time collab) ir_diff можно заменить на CRDT-операции, не меняя modification_log (поле diff_json становится opaque).

ЭПИК 4: Интерактивная State Machine и Адаптивный Роутинг

EP4.ST1 — Определение состояний и переходов State Machine

Суть: Явная FSM с состояниями: IDLE → PLANNING → GENERATING → VALIDATING → (REPAIRING ⇄ VALIDATING) → DONE; ветка WAITING_FOR_INPUT (прерывание пользователем) и INTERACTIVE (ручная правка IR, после которой возврат в VALIDATING).
Файлы:

· src/aegis/core/fsm.py — class TaskFSM: state: State; async def transition(event: Event) -> State; таблица переходов в TRANSITIONS: dict[tuple[State, Event], State].
· src/aegis/core/events.py — enum Event: START, PLAN_READY, IR_READY, VALIDATION_PASSED, VALIDATION_FAILED, REPAIR_ATTEMPTED, USER_INTERRUPT, USER_EDIT_APPLIED, USER_RESUME.

DoD: pytest tests/test_fsm.py: все легальные переходы проходят; нелегальный (IDLE + VALIDATION_PASSED) бросает InvalidTransitionError; INTERACTIVE + USER_RESUME → VALIDATING.
Extension Point: Добавление состояния AWAITING_APPROVAL (human-in-the-loop) — новая строка в TRANSITIONS, не ломая существующие пути.

Критическое замечание по железу: qwen3.6:27b в Q4_K_M требует ~20 GB VRAM с 16K контекстом, что превышает 16 GB RAM целевой машины. Phase 1 должен либо использовать qwen2.5:7b как основную модель с fallback на 27B только при доступной дискретной VRAM ≥ 20 GB, либо перейти на qwen2.5:14b (~12 GB VRAM) как компромисс. AdaptiveRouter должен проверять не только RAM, но и наличие CUDA-устройства с достаточной VRAM перед выбором 27B.
